## 逐页解说

### 01 · 让系统管理任务的全过程

时间：00:00–01:30（90 秒）

大家可以先想一个场景：同时开了几个 AI 会话以后，我们仍然要记住哪个窗口在做什么，重新解释上下文，追问进度，再判断哪份结果可以采用。模型帮我们完成了一部分工作，协调工作却仍然留在人身上。Superagent 的理念，是让系统承担任务关系、执行状态和反馈归属这些工作。今天我们先讲这些机制，再切到本机 Demo，看看代码是否真的在 Linux 环境运行，最后讨论公司试点需要补什么。这里展示的是独立实现的可行性演示，代码修复和资料处理都有固定范围。请大家重点看过程是否可追踪、结果是否有证据、失败是否可处理。

### 02 · 连续协作需要四项系统能力

时间：01:30–03:30（120 秒）

设计文章把系统能力归纳为连续、高效并行、主动和持久。连续意味着你补充一句话，系统知道它属于哪个任务。并行意味着一个任务还在跑测试，另一个请求也可以被接收。主动意味着事件在授权范围内触发工作，无关消息可以保持安静。持久意味着状态放在外部，生命周期不依赖一个聊天窗口。四个词听起来简单，实际需要任务模型、事件路由、队列和数据库配合。我们这版能验证规则路由、异步执行和单机持久化，还没有部署语义分流、跨平台多对多订阅或全天候服务。后面每一页都会把设计理念与当前实现分开说明。

### 03 · Router 协调，Worker 交付证据

时间：03:30–05:00（90 秒）

用订单查询缺陷举例。请求进入后，Router 判断它属于新任务还是已有任务的反馈，然后派发执行。Worker 在分配的范围里操作代码、运行测试，返回差异和原始输出。人工审阅最终产物。这样 Router 不需要把所有代码和所有长日志长期放在同一个上下文里。这里还要注意，职责划分只有配合工具权限才会成为实际边界。官方文章讨论了理想分层，但公开原型的主会话仍有部分执行工具，不能把不读代码的提示词约定当作硬隔离。本项目把具体执行放入受限容器，控制端负责状态与派工，作为一个可检查的实现选择。

### 04 · 授权必须来自可信入口

时间：05:00–06:30（90 秒）

原片在三分五十五秒强调，听到消息并不代表获得行动授权。有人在正文写我是管理员，或者文档里包含一段执行命令，都不能改变系统的权限。企业接入时，身份要来自平台签名、登录状态和连接器元数据，动作要经过服务端的范围校验。当前 Demo 的 Alice 和 Guest 只是模拟身份，用来展示准入规则，不能拿来当作公司认证系统。对代码和文档变更，验收还必须绑定具体版本，否则用户看的是旧稿，系统却可能提交新稿。我们把这些规则放在确定性逻辑中，模型将来可以提出建议，但不能自行扩权。

### 05 · 一个任务可以经历多次执行

时间：06:30–08:00（90 秒）

原片把 Ticket、Assignment 和 Worker 分开。对应到我们的实现，Task 是用户希望完成的工作，Run 是一次具体执行。第一次主机没连接，任务可以失败，但目标并没有消失。连接恢复后重试，Task ID 不变，同时建立一个新的 Run ID。用户补充要求时，修订号也会变化，旧运行即使稍后返回，也不能覆盖新要求。这样的结构让失败、重试和续办都有可追溯的位置。还有一个容易混淆的点：Run 完成表示程序执行结束，Task 完成要等用户核对并验收。现场会用历史下拉框展示这两层状态。

### 06 · 反馈沿任务关系回到正确上下文

时间：08:00–09:30（90 秒）

如果用户只说再展开一点，单独看这句话没有业务含义，放回原问题才知道要补充什么。本项目按来源和线程找到任务，保存历史消息、产物和运行记录，同时在创建任务时固定资料快照。以后资料列表被编辑或删除，也不会悄悄改变这次回答的依据。官方设计还讨论了把长内容留在外部、沿对象引用找回历史，也就是 Inline、Spill 和 Chain of Recall。本版只实现了任务内记录与关联，没有实现多跳回忆和跨平台多对多订阅。数据库保存了历史，也不等于模型窗口里有无限记忆。接模型时仍需决定每次读取哪些相关证据。

### 07 · 长任务运行时仍能接收干预

时间：09:30–11:00（90 秒）

把长命令放到后台以后，页面仍然可以接受新的请求和干预。这里最重要的不只是界面不卡，而是状态要保持一致。用户暂停时，我们中止当前容器；恢复时重新建立一次执行，并不承诺从任意一条机器指令继续。用户追加要求时，系统更新修订号，旧执行的结果不能再作为新版本交付。回写时同时核对任务状态、Run ID 和 revision，才能避免迟到结果覆盖。并发槽也要考虑正在取消和清理的执行，不能刚点停止就马上把它当作资源已经释放。这样的处理让任务长时间运行时仍然可控。

### 08 · 计算、状态、执行环境可以分开

时间：11:00–12:30（90 秒）

这一页是原片复核后最重要的纠偏。十二分四十五秒的画面写着计算、状态、环境分离，并明确标注设计方向、本次未部署。它没有要求代码必须放在云端的一台专用服务器。协调循环可以在一个地方运行，任务状态放在数据库里，真正的代码和工具链则由另一个端点持有。端点可以是开发机器、虚拟机或专用执行主机，离线时相关工作仍要等待环境恢复。我们用 Colima 来模拟独立 Linux 端点，就是在验证这种分离方向。不能把这次本机验证扩大解释成云端持续在线或多机高可用。

### 09 · Colima 提供可验证的 Linux 执行端

时间：12:30–14:00（90 秒）

这就是当前实际跑起来的拓扑。浏览器把请求交给 Mac 控制服务，服务通过指定的 Docker context，把工作交给 Colima 虚拟机中的容器。每次执行一个容器，结果保存后清理。容器无网络，使用非 root 用户，只读根文件系统，不挂载宿主目录或 Docker socket，并且有限定的 CPU、内存和进程数。我们检查了实际 Docker 配置，而不只是看启动参数。代码与资料处理确实在 Linux ARM64 中完成，但控制端和虚拟机共享一台物理 Mac，电脑休眠仍会同时影响两者。这证明了跨环境派工和受控执行，没有证明容器绝对安全或系统高可用。

## 故障备用口播

主机未就绪：现在执行主机没有就绪，所以系统明确失败，不会回退成一份假成功结果。我们先打开已保存的执行记录，核对上一次真实运行的日志、差异和测试。历史证据只能说明那次执行成功，不能证明当前主机健康。恢复环境后，需要重新执行并检查本次结果。

结果与准备时不同：这次结果与准备时不同，我们先保留日志，不把它验收为成功。演示重点也包括失败能否定位、旧版本是否保留、重试是否产生新记录。

**为什么不直接运行官方原型？** 公开版本是研究原型，平台支持、执行权限和业务评测仍需结合公司环境审查。本项目用较小范围验证机制，并非官方产品部署。

**有容器就安全吗？** 本次验证了实际配置和固定工作流，没有完成容器逃逸测试或任意恶意代码评估。

**能跨 Mac 与服务器持续运行吗？** 当前使用本地 Docker context。真正远端还需要认证、租约、断线恢复与幂等结果确认。

**能自动合并 PR 吗？** 当前只有本地验收。企业写回应绑定具体版本，并受平台分支保护约束，需单独验收回滚和幂等。

**成本会降低多少？** 暂无业务基线和真实模型用量，不能给比例。先记录成功及失败任务的实际成本和人工时间。

**如何证明没有知识越权？** 当前只演示选定文档快照。正式试点要在检索前按用户权限过滤，并加入越权负例。
